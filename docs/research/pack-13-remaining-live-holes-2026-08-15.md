## 1) Locality / World-Knowledge Grounding

### Goal

Bind what the writer may put in the camera to the named place. A UK street gets UK props. A US street gets US props. The writer never US-defaults.

### v1 Rules

The player names a place during registration (or the Place record stores it). Code derives a `LocalityToken` from that string. The token is injected into the writer prompt as a code-owned contract block. The writer obeys the token. The writer does not "remember" locality — it reads the token every turn.

### LocalityToken

```typescript
interface LocalityToken {
  country: string;                          // "GB" / "US" / "AU" / "JP" / "IE" / "unknown"
  region: string | null;                    // "England" / "Texas" / "NSW" / null
  urbanRural: "urban" | "suburban" | "rural" | "unknown";
  civilianFirearmsNorm: FirearmsNorm;
  currencySymbol: string;                   // "£" / "$" / "¥" / "€"
  emergencyNumber: string;                  // "999" / "911" / "000" / "110"
  emergencyService: string;                 // "police" / "gardaí" / "keisatsu"
  pavementWord: string;                     // "pavement" / "sidewalk" / "footpath"
  slangRegister: SlangRegister;
  shopDefaults: string[];                   // common shop types (not branded names)
  vehicleDefaults: string[];                // common vehicle types
  // Derived by code from the place string. NOT generated by the LLM.
  // Injected into the writer prompt as a contract block.
}

type FirearmsNorm =
  | "no_civilian_carry"                     // UK, Ireland, Japan, Australia urban
  | "licensed_rural_long_guns"              // UK/IE/AU rural (farms, estates)
  | "concealed_carry_common"                // many US states
  | "open_carry_legal"                      // some US states
  | "unknown";                              // fallback — no firearms unless ledger has one

interface SlangRegister {
  useMetric: boolean;                       // true for UK/AU/JP, false for US
  drivingSide: "left" | "right";
  commonSlang: string[];                    // ["mate", "pub", "knackered"] / ["dude", "bar", "beat"]
  avoidSlang: string[];                     // ["y'all"] in UK; ["innit"] in US
}
```

### Firearms Rule (Critical)

```
DEFAULT: no civilian firearms on the street.

A gun appears in the scene ONLY IF:
  1. The LocalityToken.civilianFirearmsNorm allows it for the current scene type, OR
  2. The ledger already has a firearm item for a character in the scene, OR
  3. The scene type is: police encounter, military installation, licensed range, farm (long gun only), criminal hideout (code-placed, not writer-invented), or a seeded dungeon store.

Scene types that NEVER have civilian firearms (regardless of locality):
  - Ordinary pavement / high street / shopping area
  - School / playground / hospital
  - Public transport

If civilianFirearmsNorm == "no_civilian_carry" (UK, IE, JP, AU urban):
  - NO civilian handguns on the street. Ever.
  - Police may have sidearms (UK: usually not, unless Armed Response — writer may mention "armed police" only if code places an ArmedResponseUnit in the scene).
  - Farmer with a shotgun: only if scene type == rural farm.
  - Criminal with a weapon: only if code has placed a CriminalEncounter with a weapon flag.

If civilianFirearmsNorm == "concealed_carry_common" (US):
  - Civilians MAY have concealed handguns. Writer may reference this ONCE per encounter if relevant.
  - Writer must NOT narrate bystanders casually firing in a crowd.
  - Mass-shooting scenarios are FORBIDDEN (in all localities).
```

### How Locality Is Injected

```
The LocalityToken is a code block appended to the writer prompt.
It is NOT part of the LLM's memory or context history.
It is injected fresh every turn.

Writer prompt contract block (example, UK urban):
───────────────────────────────────────────────
LOCALITY CONTRACT (code-owned, do not override)
Country: GB | Region: England | Setting: urban
Firearms: no_civilian_carry. NO civilian handguns on street.
  Guns appear ONLY if: armed police unit placed by code,
  or ledger contains a firearm for a scene character.
Currency: £ | Emergency: 999 | Pavement: "pavement"
Metric: yes | Driving: left | Slang: UK register
Shops: do NOT invent branded chains unless Place record lists them.
Vehicles: no yellow taxis. Police cars have Battenburg markings.
Weather default: overcast. Sun is fine but not the default.
───────────────────────────────────────────────
```

### Deriving the Token

```
Code parses the player's place string at registration:
1. Look up the string against a country/city database (lightweight geocoder or static table).
   "Lincoln" → GB, England, urban.
   "Austin" → US, Texas, urban.
   "Kyoto" → JP, Kansai, urban.
   "Ballarat" → AU, Victoria, suburban/rural.
2. If the string is ambiguous (e.g., "Springfield"), ask the player:
   "Which country is that in?" One-tap: 🇬🇧 🇺🇸 🇦🇺 🇯🇵 Other.
3. If the player typed a fantasy name or "made-up town," set country = "unknown"
   and civilianFirearmsNorm = "unknown" (no firearms unless ledger has one).
4. urbanRural is inferred from the string or defaults to "urban."
   If the player typed "farm" or "village" → rural.
5. The token is stored on the Place record and refreshed into the prompt every turn.
```

## 2) Place-Harvest Allowlist (Map Pins)

### Goal

extractNamedPlaces currently scrapes noun phrases from prose and turns them into map pins. This produced: Chaos, Disbelief, Your Palm, Parse Designation, Eye Level, Registration. None are real places. "Eye Level" became a shop. Fix the filter so pins are real places — or show no pins at all.

### v1 Rules

A noun phrase becomes a map pin ONLY if it passes the allowlist AND does not match the denylist.

### Allowlist (Pin Must Match At Least One)

```typescript
type PinSource =
  | "player_named"                          // the player typed this place name (in chat or registration)
  | "place_record"                          // the Place record already has this location
  | "street_pattern"                        // matches a well-formed street/shop pattern (see below)
  | "code_placed"                           // code placed this POI (quest destination, seeded store, etc.)
```

### "Eye Level" Specific Fix

```
"Eye Level" triggered because the opening prose described the System panel
appearing "at eye level." The harvest extracted "Eye Level" as a noun phrase.
The writer then narrated it as a shop: "the Eye Level store."

Fixes:
1. DENYLIST: "eye level" is on the denylist (camera/position descriptor).
2. NEVER treat a System description as a Place. The System panel is UI chrome,
   not a location. No System-adjacent text becomes a pin.
3. POST-FILTER: if a harvested pin matches a known System term
   (System, Integration, Registration, Eye Level, Foundation Core, etc.),
   reject it silently.
```

### If Nothing Passes the Filter

```
If zero noun phrases pass the allowlist + denylist:
  - The map shows "You are here" with a single pin at the player's current location.
  - The map does NOT show 8 fake pins to fill a "Places: 8" counter.
  - The Places counter shows "1" (the current location).
  - As the player explores and names real places (or code places quest destinations),
    real pins accumulate.
  - An empty map is correct. A map full of Chaos and Disbelief is not.
```

### How This Interacts with Street Map vs Fog Dungeon

```
Outdoor street map:
  - Pins are real places (player-named, Place record, street pattern, code-placed).
  - Pins accumulate as the player explores.
  - The harvest filter runs on every writer output that contains place-like phrases.

Indoor fog dungeon (seeded store / instance):
  - The fog map shows rooms, not street pins.
  - Room names are code-owned (Room 1, Room 2, Boss Chamber — or authored names).
  - The harvest filter does NOT run inside a dungeon instance.
  - On exiting the dungeon, the player returns to the street map with their existing pins.
```

## 3) Opening Kit + Portrait Contract

### Goal

A natural clothes answer ("Metallica t-shirt, baggy black jeans, Doc Martens") becomes discrete inventory items + a portrait. Not one card called "Tshirt Baggy Black Jeans." Not "Portrait pending" forever.

### v1 Rules

#### Splitting the Utterance

```typescript
interface ClothesParseResult {
  garments: ParsedGarment[];
  bagExtras: ParsedBagExtra[];
  refusals: string[];                       // "underwear" protest → logged, not an item, not a gap
  rawUtterance: string;                     // the full original text
}

interface ParsedGarment {
  slot: GarmentSlot;
  shortName: string;                        // "Metallica T-shirt" — max 30 chars
  description: string;                      // description of THIS piece ONLY
  //                                           NOT the full utterance pasted onto every card
  isEquipped: boolean;                      // true for worn garments
}

type GarmentSlot =
  | "head"                                  // hat, beanie, hood, headband
  | "chest"                                 // t-shirt, jacket, hoodie, blouse
  | "legs"                                  // jeans, trousers, skirt, shorts
  | "feet"                                  // boots, trainers, sandals
  | "outerwear"                             // coat, jacket (if layered over chest)
  | "accessory";                            // scarf, necklace, watch, belt, glasses

interface ParsedBagExtra {
  name: string;                             // "phone" / "headphones" / "multitool" / "keys"
  category: "tool" | "personal" | "weapon_improvised" | "container";
  description: string;                      // short, specific to THIS item
  slot: "inventory";                        // not equipped as clothing
}
```

#### Parsing Logic

```
Input: "Metallica t-shirt, baggy black jeans, Doc Martens, backpack with phone, headphones, leatherman, keys"

Step 1: Tokenize by commas, "and", "with" (simple delimiter split).
  Tokens: ["Metallica t-shirt", "baggy black jeans", "Doc Martens",
           "backpack with phone", "headphones", "leatherman", "keys"]

Step 2: Classify each token by slot.
  - "Metallica t-shirt" → chest (contains "t-shirt", "shirt", "top", "blouse", "hoodie", "sweater")
  - "baggy black jeans" → legs (contains "jeans", "trousers", "pants", "shorts", "skirt")
  - "Doc Martens" → feet (contains "boots", "shoes", "trainers", "sandals", "martens")
  - "backpack with phone" → split: "backpack" is container, "phone" is personal
  - "headphones" → personal
  - "leatherman" → tool (multitool)
  - "keys" → personal

Step 3: Build garments and bag extras.
  Garments:
    { slot: "chest", shortName: "Metallica T-Shirt", description: "A black t-shirt with a faded Metallica logo across the front.", isEquipped: true }
    { slot: "legs", shortName: "Baggy Black Jeans", description: "Loose-fitting black jeans, worn at the knees.", isEquipped: true }
    { slot: "feet", shortName: "Doc Martens", description: "Black leather Doc Martens boots, laced up.", isEquipped: true }
  Bag extras:
    { name: "Backpack", category: "container", description: "A dark backpack, well-used.", slot: "inventory" }
    { name: "Phone", category: "personal", description: "A smartphone.", slot: "inventory" }
    { name: "Headphones", category: "personal", description: "Over-ear headphones.", slot: "inventory" }
    { name: "Leatherman", category: "tool", description: "A folding multitool.", slot: "inventory" }
    { name: "Keys", category: "personal", description: "A ring of keys.", slot: "inventory" }

Step 4: Description per item is THAT ITEM ONLY.
  WRONG: every card says "Metallica t-shirt, baggy black jeans, Doc Martens, backpack with phone, headphones, leatherman, keys"
  RIGHT: the jeans card says "Loose-fitting black jeans, worn at the knees." Nothing about the backpack or keys.
```

#### Protest / Refusal Handling

```
If the player refuses to answer about a garment slot (e.g., refuses underwear):
  1. Log the refusal: refusals.push("underwear").
  2. Do NOT create a "missing underwear" gap in the visual profile.
  3. Do NOT loop "visual profile incomplete."
  4. Do NOT create an item for the refusal.
  5. Move on. The visual profile is complete without underwear.
     A character can be fully described by: chest + legs + feet (minimum).
     Head, outerwear, accessories, and underwear are all optional.

If the player refuses ALL garments (e.g., "nothing"):
  1. Set a default: "plain clothes" (generic, era-appropriate).
  2. Generate portrait with generic clothes.
  3. The player can change clothes later via inventory (speculative v2).

If the player responds with an insult instead of clothes:
  Already locked: insults are not clothes. Do not parse. Re-prompt once.
  If second answer is also an insult: use "plain clothes" default and move on.
```

## 4) Turn Efficiency (Maximise the Happy Path)

### Goal

Most turns should be: 1 writer call + 0 image-block on the input box. Pictures generate after the committed beat is delivered. The overlay never hangs. The writer answers the asked beat.

### Happy Path Budget (Revised)

```
HAPPY PATH (1 writer call):
  intent → hidden-state check → code math/ledger → outcome token →
  → 1 writer call (2–6 sentences) →
  → code warden (strip banned names, enforce perspective, validate beat) →
  → story first, then System chrome → choices from committed beat →
  → TEXT BOX UNLOCKED →
  → image jobs run sequentially in background (do not block input)

WRITER CALL BUDGET: 1 call. That is the target.
  If the response has no body (truly empty after trimming), retry ONCE (max 1 retry, not 2).
  After that: refuse the turn with a diegetic fallback ("The moment blurs. Try again.").
  Do NOT make a third text call.
```

### What to CUT from the Happy Path

| Cut | What It Did | Why Cut | What Replaces It |
|-----|------------|---------|-----------------|
| **Graphic Novel Director** (extra LLM call) | Re-interpreted prose into panel scripts. | 10–20 second stall. Third model on the happy path. Unnecessary: code can derive panels from outcome token + prose length. | Code maps outcome token to shot type (already designed in SGM Visual dump). 1 panel for short prose (2–3 sentences), 2 panels for long prose (4–6 sentences). No LLM needed for panel layout. |
| **Choice-regeneration LLM** (extra LLM call) | Re-generated choices when the writer's choices were bad. | Second or third LLM call. Choices should come from the committed beat, not from a separate model. | Code pads 3–4 choices from the outcome token + beat type. Attack/defend/flee for combat. Talk/examine/leave for dialogue. The writer may suggest choices in its output but code validates them against the beat. If writer choices are invalid, code substitutes its own. No second model. |
| **Second empty-story retry** | Retried the writer a second time if the first retry also failed. | Three LLM calls for one turn. Diminishing returns. | Max 1 retry. After one empty retry, refuse: "The story falters. [Try again]". |

### What to KEEP

| Keep | Why |
|------|-----|
| **1 writer LLM call** | Core of the experience. Non-negotiable. |
| **1 empty-story retry** (max 1) | Catches transient failures (model hiccup, rate limit). |
| **Optional cheap rewrite** for Kid Mode / content rating | Locked: swear swap, slur mask. This is a small, fast, text-only post-process. Not a full writer call. |
| **Code warden** (post-filter) | Strips banned names, enforces perspective, validates beat fidelity, checks locality contract. CODE, not a model. |
| **Sequential image jobs after commit** | Images are valuable but must not block the text input. |

### Hung Overlay Fix

```typescript
interface TurnTimeoutPolicy {
  writerTimeout: number;                    // 15_000 ms (15 seconds)
  // If the writer call does not return within 15 seconds:
  //   1. Show diegetic "still thinking" copy: "The world shifts. One moment."
  //      (NOT "Synthesizing next event" or "Weaving narrative threads" — those are developer jargon.)
  //   2. Continue waiting up to writerHardTimeout.
  writerHardTimeout: number;                // 30_000 ms (30 seconds)
  // If the writer call does not return within 30 seconds:
  //   1. Show [Cancel] button.
  //   2. If player taps Cancel: rewind to the previous committed turn.
  //      Do NOT lose the player's intent — store it for retry.
  //   3. Show: "The story stumbled. [Try that again] [Do something else]"
  cancelBehavior: "rewind_to_last_committed";
  // CRITICAL: persist the committed snapshot BEFORE the overlay appears.
  // If the player refreshes during the overlay, they load the last committed snapshot,
  // not a stale cloud state.
  // The overlay MUST have a cancel/rewind path. No infinite spinners.
}
```

### Persist Before Overlay

```
CURRENT BUG: refresh during overlay loads an older cloud state,
  losing the finished turn.

FIX:
1. Before the overlay ("thinking") appears, persist the PREVIOUS committed turn
   to cloud storage. This is the safe rollback point.
2. When the writer returns and the new turn is committed, persist the NEW turn
   to cloud storage immediately (before images generate).
3. If the player refreshes:
   - If the new turn was committed and persisted: load the new turn. Show images
     as they arrive (or placeholders).
   - If the new turn was NOT committed yet (overlay was still up): load the
     previous committed turn. The player can re-submit their intent.
4. The HUD shows "Last saved: Turn 12" (or equivalent) so the player knows
   their progress is safe.
5. "Continue" (from a different device or after a refresh) ALWAYS loads the
   latest persisted committed turn. Never a stale snapshot.
```

### Writer Must Answer the Asked Beat

```
BUG: Player asked "what is the metallic glint I see?" Writer responded with
  stock "the knife feels reassuring" and "might be nothing."

FIX: Beat fidelity check.

1. The player's intent is classified by code:
   "what is the metallic glint I see" → intent_type: "examine_object"
   The outcome token includes: EXAMINE_OBJECT { targetHint: "metallic glint" }

2. The writer receives the outcome token. Its contract is:
   "The player examines [targetHint]. Your prose MUST:
    - Name or describe the object (what the glint is).
    - If the object is a ledger item: name it exactly.
    - If the object is environmental: describe it clearly.
    - Do NOT deflect with 'might be nothing' unless the ledger says
      the object is truly hidden (stealth check failed).
    - Do NOT repeat a previous turn's stock line."

3. Code warden post-check:
   - If the prose contains "might be nothing" or "could be anything" AND the
     ledger has a visible object matching the hint: REJECT. Re-prompt once.
   - If the prose repeats a phrase from the previous turn (fuzzy match >80%
     overlap of a sentence): REJECT. Re-prompt once.

4. Residual stock detection (v1 simple version):
   - Keep a rolling buffer of the last 3 turns' key phrases (5–10 word chunks).
   - If the writer's new output contains a chunk that matches a previous turn's
     chunk at >80% similarity: flag it for the cheap rewrite pass.
   - The cheap rewrite pass strips the repeated chunk and asks the writer to
     replace that sentence. This is the ONLY use of the cheap rewrite on the
     happy path (aside from Kid Mode content filtering).
```

### System Lines: Only When the Ledger Changed

```
BUG: System showed "Tutorial: first sticky failure registered" on a look action.
  HP was 24/24. Nothing changed. A question is not a failure.

FIX: System lines fire ONLY when code detects a ledger change.

interface SystemLinePolicy {
  // A System line appears in the System chrome area ONLY IF one of these is true:
  showConditions: SystemLineCondition[];
}

type SystemLineCondition =
  | "hp_changed"                            // HP increased or decreased this turn
  | "sta_changed"                           // STA increased or decreased this turn
  | "condition_added"                       // a condition was added (poisoned, bleeding, etc.)
  | "condition_removed"                     // a condition was removed
  | "approach_closed"                       // an approach / action type was permanently blocked
  | "xp_gained"                             // XP was awarded
  | "level_up"                              // character leveled up
  | "item_acquired"                         // an item was picked up or looted
  | "item_lost"                             // an item was used, broken, or dropped
  | "quest_accepted"                        // a quest was added to the journal
  | "quest_updated"                         // a quest objective advanced
  | "quest_completed"                       // a quest was completed
  | "gold_changed"                          // gold increased or decreased
  | "talent_unlocked"                       // a talent node was unlocked
  | "combat_started"                        // an encounter began
  | "combat_ended";                         // an encounter ended (victory/flee/wipe)

// If NONE of these conditions are true this turn:
//   The System chrome area shows NOTHING new this turn.
//   No "sticky failure." No "tutorial registered." No filler.
//   The System area may still show PERSISTENT info (current HP, current STA)
//   but no NEW log line.
//
// A "look" action that finds nothing and changes no ledger state:
//   System area: no new line. Story area: writer describes what they see.
//   That's it.
```

### Perspective Enforcement

```
BUG: Settings = second person. Writer used "Jax steps… their grip…"

FIX: Code warden enforces perspective.

1. settings.perspective = "second_person" → all prose must use "you" / "your" / "yours".
   Warden checks: does the prose contain the character name as a subject?
   ("Jax steps" → third person. "You step" → second person.)
   Simple regex: /\b{characterName}\s+(steps|walks|runs|grabs|looks|turns|says|feels|thinks)/i
   If matched: flag as third-person violation.

2. On violation: cheap rewrite pass replaces "{characterName} {verb}s" → "you {verb}".
   This is a text substitution, not a full LLM call. The cheap rewrite model does it in <1s.

3. Persistent: the warden checks EVERY turn. The writer receives the perspective
   instruction in its prompt contract:
   "PERSPECTIVE: second person. Use 'you' and 'your'. Never use the character's
    name as the subject of an action sentence."
```
